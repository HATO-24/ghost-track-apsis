## 一、分工与本次交付

这份文件定义开发目标、优先级、依赖、边界和验收原则。请 6Sol 根据它编写可交给 DeepSeek 执行的任务卡，**本阶段不直接修改游戏代码**。DeepSeek 按任务卡实现、提交可审查的改动并提供运行证据；Astra 独立审查架构与结果；项目负责人决定产品取舍与合并。

本轮先明确联合战役 Demo 的产品范围，并形成 Phase A 的近期任务卡及 Phase B 的依赖拆分。后续阶段只列进入条件，不一次性要求 DeepSeek 完成全部路线图。不因有同名模块或历史测试通过就认定需求已经完成，也不重复实现已有 PR 的功能。本 R2 取代旧版将模拟器目标仅写为“完整打一场战斗”的产品口径；原有物理、信息、存档与测试要求继续有效。

## 二、项目判断与当前基线

### 2.1 已确认的产品目标

用户将战斗模拟器版定位为**剧情线之外虚构的全面战争阶段**，参考《Z 高达》格里普斯战争所带来的战争规模与多方协同感。玩家自由编制自己的舰队，与其他友军舰队协同作战，达成对第33轨道特别独立舰队（33 OSID）去军事化的目标。该参考是用户给出的创作方向，不导入其人物、势力或原作设定。

用户已明确选择首个 Demo 的范围：**一场可完整打完的联合战役：自由组舰＋AI 友军协同＋明确战争目标。** 多场战役之间持续继承损失/补给、持续战争地图、全局经济与生产不进入首版验收；保留后续扩展余地。首版按单人游玩与 AI 友军实施，不新增联网多人范围。

预期玩家流程为：理解战役目标与友军分工 → 选择舰只并编制自有舰队 → 部署与协调行动 → 根据不完整情报调整命令 → 实施交战或撤离 → 获得可解释的战果、损失与目标判定。舰队配置与协同选择必须影响这场战役的实际过程。

“剧情暂停扩写”继续适用于主线章节、角色分支和长篇演出；**战役简报、行动目标、协同通信、任务阶段与结算是本 Demo 必需内容**。`story=false` 不得连带关闭战役目标和结束判定。战役的具体年月、参战友军与正典关系由内容提案明确，不覆盖主线剧情存档和既定结局。

### 2.3 基础优先级保持，但架构要服务多舰队

当前基础瓶颈仍是跨系统一致性：物理世界、传感器输入、玩家可知信息、战斗消费者和读档恢复是否遵守同一套数据契约。近期继续收拢事实来源与恢复行为，同时提前定义舰队归属、指挥权限、逐舰状态和情报拥有者，避免修完单舰接口后再为联合战役全部返工。

## 三、P0：先协调现有 PR 与验收契约

目标是让实现和测试验证同一个设计，而不是各自通过不同的自测。

6Sol 首先产出一张“现有 PR 依赖与契约协调”任务卡：核对各 PR 的最新 head、base、修改范围和未解决意见，给出整合顺序与验证提交。不能将 #17、#19、#20 各自的成功结果相加，冒充整合完成。

必须处理两处测试口径问题：

1. **元数据存放与可见性。** #17 使用独立 `EntityCatalog` 承载静态元数据；#22 的部分断言却要求 PhysicsWorld、WorldState、snapshot 都完整保存这些字段。需求是“真值有唯一来源、需要它的消费者能正确取得”，不要求将同一字段复制到所有容器。PhysicsWorld 负责运动学，EntityCatalog 负责静态信息；合成视图应明确来源。玩家 contacts/track 还要服从证据与可见性，`batch/rcs/radius/has_pd` 不能因为是静态字段就自动泄露给玩家。调整断言时须附逐项契约映射和等强度负例，保留丢失、错误归属、静默 friend 回退与真值泄露检查。
2. **JSON 与运行时类型。** #22 A0-T3 同时检查原始 JSON 解析值及恢复后事件序号的 `int` 类型。JSON 载体与 GDScript 运行时类型应区分：原始数字检查整数数值语义和有效范围；恢复后的事件序号检查实际整数类型、顺序和续写。不能为满足载体类型断言而任意更换存档格式，也不能删掉恢复后类型检查。

交付门槛：每项失败都能归为“实际实现缺陷”“测试契约不匹配”或“尚未验证”，附证据；所有契约调整可追溯；Phase 0 门禁语义和默认 profile 保持原样。

## 四、P0：完成物理与观测事实链

需求：同一个实体在同一模拟时刻，所有需要真实几何的消费者使用同源位置/速度、参考系、单位和历元。WorldState 若提供位置副本，必须明确更新时机与投影角色；不得成为第二套独立积分器。传感器不能继续使用与场景真值无关的演示坐标。

6Sol 应先对照 #17/#19/#20 确认哪些已实现，只为剩余缺口拆卡。至少覆盖：

- 移动观察者和目标后，传感器输入几何随真实状态变化；消费者读取的是同一 tick 的快照。
- 无噪声的确定性 fixture 核对几何误差；有噪声的观测按明确误差模型验收，不能把“航迹必须等于真值”作为通用规则。
- 稳定实体 ID 能贯穿目录、物理、观测来源和消费者；玩家显示按证据匿名化。
- 缺实体、物理未就绪、过期快照和不支持参考系等路径返回明确原因，不静默回退演示值或友军身份。
- 合成 snapshot、HUD 和火控消费路径都纳入验证，不能只检查服务内部函数。
- 提前区分实体 ID、舰队归属、势力关系、指挥权限与情报来源；`friend` 不等于玩家可直接指挥，也不等于玩家立即知道其全部观测。每艘舰的装备/弹药/燃料/损伤不能共享一份默认旗舰状态。
- 唯一物理真值与分方情报可以并存。分别明确玩家、友军舰队、敌军可读的观测与已共享航迹；AI 不能通过直接读取敌方隐藏真值获得全知能力。无需本阶段强制新建多套复杂航迹系统，但情报读取与共享边界必须可验证。

每张相关任务卡必须说明坐标系、距离/速度/时间单位、采样时机、误差阈值及阈值依据，不让实施者自行猜测。

## 五、P0：存档后能连续、正确地继续模拟

目标：读档恢复的是可继续运行的同一场模拟，而不是只恢复近似画面。请分成独立小卡，避免一次重构整个 GameSession。

| 切片 | 要求 | 核心验收 |
| --- | --- | --- |
| 事件历史与续写 | 恢复整数序号、分配器与 ID 去重信息；只规范化有明确契约的字段 | 内存和文件往返后序号/顺序一致；继续发布无重复 ID；恢复历史不重复派发；浮点时间/载荷保真；非法序号明确拒绝 |
| 旧档兼容 | 缺 bus 或缺新增元数据时有明确迁移策略 | 旧档能按支持策略读取；超过历史缓冲上限后，重放可恢复的已用 ID 不得在迁移时丢失；未支持版本明确拒绝 |
| 传感器状态 | 保存/恢复 EMCON、雷达开关及必要通道运行态 | 保存前主动改变状态、建立非空通道；读档比较规范化内容，并继续推进验证后续输出，不只比较通道数量 |
| 通信恢复 | 定位真实 HUD 会话读档重放中的 `no_route` | 从真实入口复现并修复；保留投递/延迟语义；不能以跳过消息或吞掉错误获得成功 |
| 长时运行成本 | 量化全日志重放的体积和延迟增长 | 固定种子、指定 tick 数及环境记录体积/保存/读档耗时；先测基线，再由任务卡写明预算，避免无依据承诺 |

其中通信 `no_route` 来自 #22（head `8bf7517`）A0-T3 的真实 HUD 会话往返记录与探针说明，不来自误派工实验；本轮未独立重跑该路径。DeepSeek 应在任务卡指定的最终整合基线上先复现。

事件切片应包含本轮发现的边界：如果只用最后一段环形缓冲重建去重集合，可能丢失旧档操作重放已经恢复的较早事件 ID。禁止用全局“把数字转 int”修复事件序号问题。

联合战役运行层接入后，存档契约还要覆盖参战名册与实体映射、逐舰资源/命令、敌我 AI 当前任务、协同请求及回执、在途通信/弹体、战役目标与结束状态、已共享情报和随机状态。恢复后不得重复出兵、重复扣弹或重新结算目标；同一战役种子与有效存档应支持可解释的连续行为。上述内容随对应系统增量接入，不要求在系统尚不存在时先造空快照。

### 6.1 首场联合战役的必做能力

**组舰与部署。** 以可用舰只/舰级为选择池，允许多种有效组合并显示组合带来的能力差异。角色槽位、预算、补给或指挥容量应有明确用途；现有 13 舰名册与 8 类角色槽位属于旧实现约束，不自动成为用户对“自由组舰”的最终定义。6Sol 提出首版组合规则及可用舰型，不擅自承诺无限舰数、任意复制同一命名舰或完整造舰经济。编制确认后，每艘舰以稳定 ID 进入场景，带入正确配置；提供至少两套有实际差异且可完成任务的合法组合。

**逐舰指挥和战斗。** 玩家可以向自有舰队或选定舰组下达意图，具体舰只按自身能力执行。明确发射者、命令接受者、授权、射击预测和各自资源账本；显式指定无效发射者或越权指挥时拒绝，不能悄悄换成旗舰。编制中的“角色”与空间上的运动队形分开；首版只实现任务所需的最小跟随/护卫/机动行为，不预先扩成任意复杂编队编辑器。

**AI 友军协同。** 至少一支拥有独立任务与指挥权的 AI 友军舰队真实参战。首版建议玩家直接指挥自有舰队，对其他友军发送协调请求，例如支援某目标、掩护某区域、约定行动窗口或协助撤离；具体请求种类与指挥权关系由 6Sol 在任务卡中提案。请求有已发送、收到、接受/拒绝、执行、完成/失败等可解释状态；遇到资源不足、链路中断或战损不能假装执行。玩家应能看到友军已报告的计划、预计到达与受阻原因，但不能因此获得敌方全知位置。

**敌方行动。** 第33舰队参战部队需要最低可用的战斗决策：按有限信息执行守卫、攻击或撤离等场景任务，并对玩家与友军行动作出响应。允许首版采用数据驱动的规则 AI 与固定行动计划，但其执行必须走实际通信、机动、授权、弹药和战损系统；不能依靠删除敌舰、瞬移友军或写死胜利时间来完成战役。

**目标与去军事化判定。** 把“使第33舰队失去有组织武力行动能力”落实为可观察、可结算的任务条件，例如解除指定作战单位的有效战力、切断关键军事指挥能力、控制指定军事节点。这里的例子是待定方案，6Sol 应提出最小目标组合、明确适用对象与阈值，再交用户核对；不把全灭、击毁民用设施或完整占领/登舰系统擅自列为必需。暂时断联或短时停火不能无条件算作永久解除武装；撤离、失能、投降等状态只有存在对应机制和判据时才可计入。

战役范围必须与胜利表述一致：若本场只是对第33舰队某分遣队的行动，结算应明确是去军事化进程中的阶段性成果；只有场景确实覆盖并满足设定的决定性军事能力解除条件，才可宣告整体目标达成。不能用局部击杀数直接声称整个第33舰队已去军事化。任务判定层可读取用于裁决的真实状态，玩家目标面板则按可用战报/情报更新，不能泄露尚未观测到的隐藏单位。

**战役结束与反馈。** 明确成功、失败、主动撤离及必要的僵局/时限处理，并提供目标依据、敌我损失、资源消耗和友军贡献。合理设计玩家的关键职责，使协同请求和舰队选择能改变结果；避免玩家完全不行动时友军总能包办胜利，或友军只在背景文本中存在。

### 6.2 首版规模与验收边界

- 已确认范围是一场联合战役，不含跨战役持久化战争地图；战役内部允许多个行动阶段。
- 规划起点建议为一个受控战区、玩家一支舰队、至少一支 AI 友军舰队和第33舰队参战部队。确切舰数、时间跨度、弹体数量上限、AI 更新频率与目标复杂度由 6Sol 提出性能预算，需经过实际测量，不将建议数量写成用户已确认设定。
- 首版优先复用已有舰型与基础模型。允许战前配置和战场资源消耗，不以实现完整港口补给、船坞制造、政治外交、全舰队投降谈判或多人联机为前提。
- 必须从正式入口走通“简报→组舰→部署→协调→战斗→结束→战报”，不能只从测试脚本构造最终胜利状态。
- 至少验证两套合法编制；发射/受损不会串改另一艘舰的资源；未选舰不会参战；不合法编制在部署前给出原因。
- 至少验证一次有效协同改变实际态势，以及拒绝/失联/友军战损时的执行与玩家反馈；敌我 AI 均受其可知信息和真实能力约束。
- 验证胜利、失败、撤离和目标尚未完成时不提前结算；关键节点的存档恢复不能重复部署、重复命中结算或重复发奖。
- 在任务卡约定规模下记录模拟步耗时、AI 耗时、帧耗时/响应、存档耗时；补充实际游玩与界面验收。基础探针通过不替代战役的可玩性与平衡检查。

### 6.3 建议的 Phase B 拆分顺序

6Sol 按依赖细化以下需求包，不将它们视为已经批准的具体实现设计：

1. **B0：联合战役数据与权限契约**——参战舰队、单舰实例、编制到部署映射、指挥/情报边界、目标生命周期；可在 Phase A 收尾时先设计。
2. **B1：自由组舰到多舰真实战斗**——编制选择、部署、逐舰命令/资源/损伤、基础舰组操作与存读档。复用已有弹道和火控，不重复实现。
3. **B2：最小敌我舰队 AI 与协同**——场景任务执行、协同请求/回执、共享情报、失联/战损处理；包括让用户能理解这些行为的最低 UI。
4. **B3：首场联合战役内容与目标结算**——选定参战阵容、去军事化目标、简报和任务阶段；与 B1/B2 按明确接口并行准备内容，最后在同一版本整合验收。
5. **B4：可玩性、负例与规模验证**——不同组舰方案、成功/失败/撤离、AI 反应、存档、性能与实际游玩；形成首个 Demo 交付结论。

## 七、6Sol 应输出什么

请先交付**一页联合战役范围表**：分别列出用户已确认项、你的首版建议、需用户决定的产品项、后续范围。然后交付近期任务队列、PR/任务依赖图、Phase A 第一批可执行任务卡，以及 B0–B4 的待细化任务包与成本判断。

Phase A 首批仍涵盖契约协调、已有实现链整合验收、事件存档连续性；传感器持久化和通信恢复另列卡，提前写入多舰队的指挥、情报和逐舰状态边界。不要因为产品目标扩大就暂停基础修复，也不要仍以“单旗舰能打一场战斗”作为模拟器 Demo 的最终完成标准。凡会改同一核心文件的卡，要规定顺序或局部接口边界。

每张卡必须具备：

1. 玩家或模拟行为层面的目标，以及可复现的当前问题。
2. 当前基线提交、前置 PR/任务、允许修改范围及明确不做的内容。
3. 状态的权威写入者、读取者、单位/时间/可见性契约。
4. 实施步骤与提交拆分；对真实缺陷先有失败证据，再实现修复。
5. 正例、负例、兼容性、同 tick/持续运行等相关验收，不写仅照抄实现的空洞测试。
6. 明确的运行命令、日志/报告位置、预期结果和完整回归要求。
7. 旧失败转绿、计数漂移、新增失败分别如何报告；只有证据充分才更新对应基线，不能自动刷新期望值来消除红灯。
8. 交付物、已知限制、待独立审查项目和后续依赖；完成代码不自动等于获准合并。

测试必须对应同一最终提交。保留原始失败和日志；不跳过失败、不放宽精度、不吞异常、不用 `continue-on-error` 伪造验收。分别报告“全部通过”“无新增回归但存在既有失败”“尚未验证”。按既有失败基线返回成功的 CI 也必须展示真实失败数。
