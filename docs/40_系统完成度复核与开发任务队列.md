## 0. 执行结论

**当前状态判断：已经积累了很多独立系统与验证工具，但不能仅凭文件数量和各模块的历史 probe 结果，认定“真实地月轨道战斗模拟器”已端到端完成。** 最大风险不是从零缺少每个系统，而是多版本实现、模块边界和权威状态流未完全收敛；交通管制、港口/对接、EW、改装与可视化均有不同程度的局部实现，但“一个由玩家操作、以同一物理世界为准、能完整结束一场战斗”的集成证据仍不足。

本次仓库树盘点得到约 1,473 个路径，其中约 272 个 GDScript、54 个 JSON、32 个 Godot 场景，以及约 148 个名称含 test/probe 的路径。主线包括 `game_v15`、`game_v16`、`game_v17`，另有 `cislunar_explorer` 和 `sensor_explorer` 验证台。这样的体量代表已有投入，也使单一事实来源和集成回归成为最高优先级。

本审计采取的判断口径：

- **模块存在**：有服务/模型/内容 schema/API；不自动等于游戏里已可用。
- **模块自测**：有 probe 或文档记载 PASS；不自动等于当前提交在运行时通过。
- **集成可用**：从正式运行入口装配，使用同一权威数据，通过玩家操作推动系统，并有端到端测试证明。
- **符合目标**：除实现外，还满足设计书中的真实轨道、延迟/不确定信息、战斗授权、视觉约束、可维护和扩展要求。

### P0 当前要先解决的事情

1. 明确并固化无剧情的模拟器开发 profile；完整剧情扩写暂停，但保留故事系统和现有剧情接入契约。
2. 统一权威物理世界、世界实体位置/速度、轨迹图、传感器、火控、弹道及碰撞/对接的时间和参考系。
3. 建立由观测到毁伤报告的完整战斗闭环，用真实弹药、授权和时间流程验收。
4. 统一航迹/IFF/识别/EW 的证据与状态写入者，避免旧版/新版各自判定。
5. 将交通管制、机动、接近、对接、港口服务和加注/维修接到真实物理状态。
6. 恢复并测试高密度四区 UI 的态势图图层，而不是另增一套脱离物理的展示页。
7. 让 headless probes 与真实入口集成 smoke test 可一键复跑。本轮并未运行 Godot，因此不把过去文档中的 PASS 记作本次通过。

## 1. 关键现状与证据

### 1.1 运行入口和构建配置

- `game_v17/project.godot` 当前主场景是 `res://main_menu.tscn`。
- `game_v17/framework/content/build_profiles.json` 当前默认 profile 是 `full`，且开启 story/prelude/triggers。
- 配置里的 `combat_sim` 关闭 story/prelude/triggers，但其功能表里 `traffic=false`、`port=false`，而 `sandbox_opts` 又默认启用 unlimited ammo、auto authorize、quick restart。它适用于便捷展示/测试的倾向高于拟真战斗验收。
- `game_v17/scripts/ui/main_menu.gd` 会按 BuildProfile 在 sandbox 情况下跳过菜单进入 profile 指定场景；`game_v17/scripts/ui/shell_binder.gd` 有把场景转换成 GameSession seed 并组装可选系统的逻辑。因此无需先推倒重做启动框架，应该先把 profile 的定义、系统装配、日志与启动测试固化。
- 配置缺失时的回退行为需要以 profile probe 与真实启动日志验证，不能只读配置文件判断成功。

### 1.2 物理与实体状态

- `game_v17/scripts/core/physics_world.gd` 具备 CR3BP/RK4、固定步长、实体状态、参考系转换、Jacobi/能量诊断、保存/加载和契约检查等方法。
- `game_v17/scripts/core/game_session.gd` 的 `tick()` 依次推进时间、PhysicsWorld、订单/通信、弹道、传感器与航迹、EW/信号、Combat/Port、损管与交通等服务。
- 但 `GameSession.sync_world_from_physics()` 明确是一个**显式同步 API**，注释说明“不自动同步、不双写”，而 `tick()` 的常规流程不直接显示调用该方法。必须验证弹道、sensor snapshot、TrackTable、UI 与目标预测各自读的是哪份最新位置/速度；不要假定推进物理即意味着所有消费者自动同步。
- 另一条历史路径仍在：`scripts/state.gd`、`scripts/orbit_model.gd`、`scripts/plot.gd`、`scripts/framework_bridge.gd` 以及 `framework/sim/cislunar_physics.gd`。后者的文档/注释把 CR3BP/RK4 描述为独立验证/可选 shadow 模型，不是 JPL 星历。仓库目前至少存在值得厘清的旧轨道/展示链与新 GameSession PhysicsWorld 链。
- 设计文档规定 ECI 为积分参考系、LVLH 用于相对运动/展示、BODY 用于舰体姿态；现有模拟器 sandbox 又使用 barycentric rotating frame（`bary_rot`）。需要明确转换、历元、轴向和单位约定，禁止把局部坐标当惯性坐标或把显示适配器称为权威物理。
- 当前模型应准确称为规定精度下的 CR3BP/RK4 近似，直到经过验证的星历与摄动模型完成前，不应声称是完整 JPL 级精度。

### 1.3 传感器、IFF、识别和 EW

- `scripts/core/sensor_service.gd` 会输出 observation/evidence，再由 `GameSession._advance_sensors()` 以白名单路由到 TrackTable。此处已有可用的管线骨架。
- `framework/sim/sensor_authority.gd` 仍明确标注 shadow/advisory、`authoritative=false`，其说明也将 IFF/ELINT 视为未纳入完整 authority 的部分。
- `scripts/state.gd` 保留旧版 V15 融合/等级/身份写入路径。仓库中的 `docs/38_传感器与信息作战规格.md` 和 `game_v17/docs/sensor_authority_plan.md` 提醒过多套感知事实源问题；后者也记录过 legacy V15 authority 的历史基线。由于 GameSession 已有另一条 SensorService/TrackTable 路径，实现前必须更新当前架构图与文档，不应把旧迁移计划无条件当成当前全部事实。
- `scripts/core/transponder_service.gd` 和 `identification_service.gd` 已有应答机/证据处理服务，应该与 TrackTable 的可信证据管线统一，而非让 IFF 查询本身永久直接设置 friend/hostile。
- `scripts/core/ew_service.gd` 是围绕信息作战模型的效果/持续时间/衰减接口；其文档明确不做波形/射频物理仿真，也不直接写 world/TrackTable/UI。因此 EW 当前适合称为**可测的抽象效果服务**，高拟真 EW 仍需要将干扰/欺骗对观测、航迹质量、通信和火控的影响接到同一管线，并明确模型精度边界。

### 1.4 战斗、弹道与损伤

- `scripts/core/combat_service.gd` 有 ROE、TRACK/SOLUTION/FIRE 授权、火控解算、射程/冷却/弹药与发射 API。
- `scripts/core/combat_ballistics.gd`、`combat_planner.gd` 与 `DamageService` 提供了进一步整合基础；GameSession 内已有 combat damage event 的路由及按 shot id 去重的逻辑。
- CombatService 自身文档明确最终命中由弹道/损伤集成负责。多个独立 probe 通过也无法证明正式入口中传感器航迹、物理位置、火控解算、弹体飞行、目标机动/点防、伤害、战损退化和报告形成同一个闭环。
- 拟真 profile 不应靠无限弹药和自动授权让展示流程看似顺畅。快捷选项应只存在于明确的 test/sandbox profile，并在 UI 中清楚标识。

### 1.5 交通管制、导航、对接和港口

- `scripts/core/traffic_control_service.gd` 提供设施/航道/容量/窗口/队列/许可/OTC/NPC/伪装线索；其文档明确不执行真实物理、泊位/加注/损伤或真实 RF。
- `framework/core/navigation_model.gd` 文档将自己定位为规划层，当前抽象路线与交通许可不直接改轨道物理。
- `framework/sim/docking_controller.gd` 有接近走廊、端口、姿态/速度门限和对接 FSM，但文档明确它是不接物理推进、不写 world 的纯几何模型；`docked` 状态需上层权威世界消费。
- `scripts/core/port_service.gd` 有请求、许可、接近/对接状态、泊位与拖船资源、加注、维修、离港等业务 API；存在该 API 不等于位置、端口约束、推进剂、质量和损伤已写回同一个仿真世界。
- 所以交通管制、停泊入港、维修和加注的重点是跨服务一致性、资源原子性和物理状态联动，而不是继续堆更多孤立状态机。

### 1.6 舰船改装与资产

- `scripts/core/refit_service.gd`、`fleet_refit_service.gd`、`ship_catalog.gd` 提供目录、模块、槽位、资源、提交队列、舰队实例和保存/检查接口。
- 下一阶段必须验收模块安装后是否真实改变推进剂/质量/Δv、加速度、热管理、RCS/签名、传感器/火控能力、伤损结构/端口与模型构型。只看改装列表/资源扣款不算完成。
- `game_v17/models/` 有程序化 `ship_model.gd`、`station_model.gd`、`habitat_model.gd`、`asteroid_habitat_model.gd`、`asteroid_fortress_model.gd` 等及若干场景，包含环形/圆柱居住构型、小型站点与小行星设施方向。
- `game_v17/docs/models_3d.md` 已把当前模型定位为展示资产，并注明当前缺少贴图/法线/粗糙度/LOD/碰撞/动画/真实尺度装配和真实物理交互，且一处记录了未跑全量 regression。
- 资产美术方向应使用用户提及作品的高层设计原则而非复制其可识别资产：殖民地巨构要兼顾强轮廓与工程可信度；小型空间站应有真实模块、桁架、散热和对接功能；舰船以推进、燃料、散热、传感器、武器与装甲布局读出战术用途，并适度贴合本作设定。

### 1.7 UI、态势图与分层

- `docs/09_UI设计.md` 同时记录了 V1.5、V2 框架与 V17 HUD 等多阶段 UI。实际仓库中的 `scripts/hud.gd`、`scripts/plot.gd`、`scripts/ui/plot3d.gd`、`scripts/ui/v1_hud.gd` 与多种独立页/overlay 并存。
- 关键类体量较大：`game_session.gd` 约 4,873 行、`state.gd` 约 3,991 行、`plot.gd` 约 3,488 行、`v1_hud.gd` 约 4,190 行、`framework_bridge.gd` 约 2,118 行、`shell_binder.gd` 约 1,802 行。行数本身不是质量结论，但这些类承担多类状态编排、输入、绘制与适配，意味着必须将权威写入者、视图模型和模块边界明确化，并采用渐进式拆分。
- `scripts/ui/near_view.gd` 的注释明确当前近景 SubViewport 是只读展示，不接物理/truth 位置；真实位置/姿态/构型的可视化联动也需验证。
- 由于本轮未执行 Godot、不曾录制新截图，也未做历史 commit 的逐帧比对，**不能断言具体是哪一项态势可视元素在哪个提交丢失**。第 #8 号 Issue 要求对照 mockups/历史提交建立 checklist 与 golden screenshots，而不是臆测删改原因。
- 统一 UI 应保持设计文档要求的 V1 高密度四区、薄荷绿/琥珀色、细线框与终端风格；所有图层来自同一 authority 的只读 VM，并可显示 LIVE / ADVISORY / UNAVAILABLE。旧 UI 可作显式回退/开发预览，但不应成为第二套系统事实来源。

### 1.8 测试、维护与 mod

- 仓库含大量 `game_v17/tests/*_probe.gd`，覆盖战斗、弹道、物理、传感器、EW、IFF/transponder、traffic、docking、refit、存档和 profile 等方向。
- 多份 docs 记载历史 PASS 数，但本审计没有运行当前 main 的 Godot 可执行文件，也没有确认每个脚本按当前依赖顺序实际通过。
- 在所检查的仓库树中未发现 `.github/workflows` 路径；应以新增 CI/回归入口固化实际执行结果。若仓库还使用外部 CI 或隐藏执行配置，应在实施时补充文档。
- 当前已有不少 JSON content/schema，这是数据驱动和 mod 的好基础。本次静态检查没有确认存在完整公开 mod manifest、依赖冲突/覆盖规则、脚本沙盒与 save/mod 兼容策略；应把这些作为明确需求，不要假定 JSON 文件存在就等于 mod API 完成。

- **部分完成**：有服务/模型/API/局部 UI 或 probe，但缺少端到端集成证明或明确仍有边界限制。
- **未验收**：当前没有本轮运行时/集成证据；不代表完全没有代码。
- **高风险**：多实现/多写入者/系统间状态可能不同步，应先于新功能解决。
- 这些等级是本次静态审计判断，不是自动测试结果。

## 3. 不可破坏的运行时契约

以下是后续任务统一使用的验收规则；如某项实现与现状不符，先做兼容层/迁移步骤，不应直接跨层写字段。

### 3.1 数据权威与依赖方向

```text
Profile / Scenario / Content schemas
                |
                v
GameSession / Simulation Clock / EventBus
                |
                +--> PhysicsWorld (唯一实体运动状态写者)
                |        |--> world/entity snapshot
                |        |--> docking / traffic geometric checks
                |        |--> weapon/ballistic initial state
                |        +--> tactical plot read-only VM
                |
                +--> Sensor models --> observation/evidence events
                |                         |
                |                         v
                |                   TrackTable/Track Authority
                |                         |
                |                         +--> normalized contacts/identity/confidence
                |                                   |
                +--> IFF/ELINT/EW/comms evidence/effects --+
                |
                +--> Combat authorization/fire-control --> ballistics/intercepts
                |                                             |
                |                                             v
                +----------------------------------------> DamageService
                |
                +--> OTC/Navigation/Port/Docking plans --> command executor
                                                         |
                                                         +--> PhysicsWorld
UI/HUD/Plot --> read view-model + submit command/request; never write authority
Story runtime --> consume domain events + submit high-level intent; never mutate simulation internals
Mod/content --> validated data + versioned APIs; no trusted arbitrary runtime script in v1
```

这个图是目标架构，不代表当前代码已经全部这样工作。第 #2、#3、#4、#6、#8、#10、#11 号 Issue 必须把关键迁移实现出来并以 probe 证明。

### 3.2 每个实体必须有可验证状态

- `id`、kind/class、阵营/身份证据、configuration revision。
- 权威位置/速度、frame、单位、历元/仿真时间与 state source。
- 姿态/角速度、质量、推进剂、可用 Δv、推力/加速度。
- 传感器阵列/武器挂点/对接端口/散热器和损伤分区等构型。
- 所有跨服务引用都以稳定 ID 关联，不以列表序号、屏幕位置、固定故事节点或硬编码舰名做业务分支。

### 3.3 信息状态不互相替代

- **观测质量**（如 L1–L4）不等于真实身份。
- **身份**不等于威胁等级。
- **威胁等级**不等于交战授权。
- IFF 回答是证据，不是永恒不变的真相。
- EW 应影响证据、链路或火控质量，但不能直接将 UI 目标标签改成一个未经权威验证的新身份。
- UI 不自己重做任何识别/射击结果判定。

### 3.4 物理真实性的边界

- 先保证单位/坐标/时间契约、轨道动力学和真实状态流正确，再按优先级叠加摄动/星历。不能靠扩大显示坐标、把船静止在图上或在开火瞬间用范围阈值代替弹道。
- 所有近似必须在 profile、scenario 或 VM 中可识别；物理初始化失败、传感器不可用或视线被遮挡时，UI 应显示原因。
- 命令是带授权、执行时刻和约束的 intent；预览无副作用，点火/执行才改变权威物理状态。执行中止要按已发生的 Δv/资源计账。

## 5. 给 DeepSeek v4.1 Flash 的交接规则

每张 Issue/PR 都必须遵守：

1. **先复述任务范围与依赖**，列出将读/改的文件、数据契约与风险；未经任务必要不得顺手重构其他系统。
2. 开始编码前读取本文件、目标 Issue 中列出的当前文件和相关 docs，检查是否有后续提交已改变所述事实；若文档与代码冲突，先更新基线而非机械照旧文档实现。
3. 先新增/更新 probe，再用最小改动通过它；然后跑受影响的现有 probes，最后跑主入口 smoke。必须给出本次实际命令、Godot 版本、退出码和 PASS/FAIL。
4. 任何 probe 未执行，都必须写 `NOT RUN`，不得复制历史文档中的 PASS 数当作本次结果。
5. 不允许将“创建脚本/JSON/场景”记为系统完成。完成必须包含服务已在预期 profile 装配、权威状态影响真实消费者、UI 有对应可观察结果、失败路径可测试。
6. 单一写者；UI 只读 VM；Domain 不依赖 UI；StoryRuntime 只消费事件和提交高层意图；mod 不可跳过 schema/版本检查。
7. 物理、sensor、combat、traffic/port/refit 的重大更改需要带可回退 profile，直到新模式通过端到端门槛。不能默默改变默认 profile 或丢弃旧剧情接入路径。
8. PR 必须说明：实现了什么、没实现什么、权威与状态流如何变化、兼容影响、已跑的测试、未跑测试、截图/性能影响、必要的 migration。
9. 资产任务须说明原创性与来源；参考作品只用于提炼设计原则，不复刻商用作品的具体模型/标志/独特细节。
