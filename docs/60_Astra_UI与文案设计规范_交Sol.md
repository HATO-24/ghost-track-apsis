## 3. 视觉语言与字体

### 3.1 保留的风格

- 深色终端底、细分区线、明确对齐、紧凑表格、矢量轨道/方位图、等宽数字和稳定的读数位置。
- 常态信息以低刺激的绿白文字呈现；磷光绿强调选中/有效读数；琥珀用于需要注意的状态；红色用于明确危险/失败。敌我、未知与选中另有形状、边线和文字，不只靠颜色区分。
- 常态保持安静。短促扫描或辉光用于选中、更新、告警；装饰层不能持续遮蔽文字或抢夺注意力。提供关闭扫描线、辉光和减少动态的设置。
- 保留必要留白，让地图和重要读数有主次。无意义随机字符、假数据和重复技术标语不作为装饰填充。

### 3.2 字体与配字

中文正文、操作和状态使用清楚的无衬线字体；数字、时间、单位、批号使用稳定的等宽或等宽数字样式。英文缩写保留在有实际意义的术语中，例如 ROE、IFF、Δv；不强制所有标题、按钮和字段中英双写。中文界面优先中文操作语句，必要英文名在详情或首次说明中提供。

以 1920×1080、100% 显示比例作首轮标定：主要操作/状态建议有效字号 14–16 px，次要数据建议 12–14 px，关键标题/读数更大。这里指最终可见尺寸，不是要求直接把所有 Godot token 改成同一个数。6–9 px 不承载必须读懂的文字；不能为塞下更多行逐步缩字号。实际字号、行高与密度须在 1600×900 和增加 UI 缩放后一起验收。

统一中文与数字基线、行高、单位间距和小数位。采用实际加载字体的宽度/ascent/descent 测量，核对字体资源打包与系统回退；不能只凭固定 `字号+偏移` 假定所有字体都对齐。长舰名可省略并可展开完整文本；命令对象、失败原因、单位和关键数值不得被无提示截断。

## 4. 固定空间分工与渐进呈现

沿用早期四区的读法，并保留全局顶栏：左侧找对象、中间看态势、右侧判断与操作、底部追踪执行。联合战役增加的信息优先进入相应区域，不另外叠一套常驻面板。

| 区域 | 常驻信息 | 按需展开 | 不在这里常驻 |
| --- | --- | --- | --- |
| 顶栏 | 任务/模拟时间、暂停与倍率、当前主要目标摘要、必要全局告警 | 全部目标、详细链路、其他计时器 | 引擎来源、模块名、所有倒计时、实现边界 |
| 左栏 | 我方舰队/友军/接触的分组摘要，选中对象，少量关键异常 | 展开某舰队成员或某组接触；排序/筛选 | 全部舰只的完整参数、重复详细战报 |
| 中央态势图 | 空间关系、可见航迹、当前命令/目标和紧急威胁 | 与选中目标或当前任务有关的火控/传感器/协同图层 | 所有目标全部标签、长帮助文字、全量开发统计 |
| 右栏 | 选中对象的身份/情报状态、当前任务、主要风险和相关动作 | 火控、证据、损管、协同等详情页 | 与当前对象无关的完整系统规则或全局日志 |
| 底栏 | 待处理/执行中的命令与重要通信摘要 | 完整命令时间线、通信历史、报告与回放 | 每个 tick 的模块事件、重复成功提示 |

列表位置与命中区保持稳定。上下文可以改变内容，不随每次点击把核心操作搬到新位置。普通更新不夺走选择或焦点；新告警可高亮/提示计数，用户打开后再定位详情。

### 4.1 四个信息层级

1. **必须立即知道**：来袭、危险接近、关键命令失败、失联、目标窗口即将关闭，以及影响行动的暂停/倍率/回放状态。短而明确地常驻或告警。
2. **当前对象与动作所需**：可用武器、所选舰剩余资源、开火阻断原因、协同请求状态。跟随选择显示。
3. **供核查和学习**：证据来源、测量时间与不确定性、详细损伤、规则解释、完整事件历史。展开后可达；重要失败原因不能只放悬停提示。
4. **开发诊断**：组件类名、`source`、`truth=false`、原始 reason code、栈、字段 ID、逐 tick 事件。开发模式中显式开启，正常游玩默认关闭。

数据来源若影响玩家判断，翻译成有用信息，例如“友军报告 · 12 秒前”“方位观测”“估算距离”，放在对象详情或相关读数旁。显示层的技术承载者不需要占据主画面。

### 4.2 联合战役的密度规则

- 左栏可折叠舰队，默认显示玩家关注的编组与异常；当前已知接触数量不能偷带隐藏实体总数。
- 地图优先标记选中对象、正在交战的对象、任务相关对象和紧急威胁。其余保留符号，按缩放/悬停/选择展开标签；信息隐藏不得变成物理或情报数据删除。
- 未选中的友军舰队以当前任务、联络状态、最近报告为摘要。选中后再展开单位和协同历史；“友军”与“可直接指挥”必须明确区分。
- 告警按严重度和对象聚合重复项。不要不断弹“成功”；命令的等待、送达、执行和失败状态保留在队列中，不合并成一个模糊的“完成”。
- 避免同时开启多层全屏模态。长文/舰队编制可以独立工作页；常用目标详情和协同操作优先右栏。模式切换保留所选舰、缩放和态势位置。
- 战术数据显示来自允许玩家读取的视图；不因需要标签或目标计数回读全知实体表。缺数据时不能展示为正常值、零值或已知身份。

## 5. UI 文案编辑规则

每段常驻文字必须帮助玩家回答至少一个问题：**这是什么？现在怎样？我能做什么？为什么做不了？** 不回答这些问题的实现说明默认迁出玩家界面。

| 文本类型 | 写法 | 位置 |
| --- | --- | --- |
| 动作 | 动词＋必要对象；例如“请求支援”“取消命令”“查看证据” | 按钮；常见目标为 2–6 个汉字，以语义完整为准 |
| 状态 | 直接状态；例如“等待回执”“执行中”“已失联” | 对象/命令所在行，不另添“当前状态为” |
| 阻断/失败 | 简短原因；有明确补救时再给动作，例如“未获开火授权” | 靠近受阻动作；详细条件可展开 |
| 结果 | 描述已发生的事实，区分请求被接收与动作已执行 | 原控件状态或队列；普通成功避免反复弹窗 |
| 教学/解释 | 首次需要时解释规则，可再次查阅 | 可关闭教学、帮助或详情，不常驻每个面板副标题 |
| 缺失/未实现 | 按真实原因区分“未知”“尚未收到”“数据不可用”“此模式未提供” | 受影响字段/功能；不能统一改为“正常”或空白 |

不使用“点击按钮即可”“本功能将会”“仅输出评估与事件”等常驻旁白。短语缩写不能模糊授权、身份、时间和结果。例如“请求已发送”“请求被接受”“任务已完成”必须保留区别；ROE、开火授权与身份识别不能互相替代。

不进行盲目的全局字符串替换。同一个 `NOT READY` 可能代表初始化、组件缺失、证据不足或动作受阻，应先查产生条件，再决定文案。既有军语与实体名优先遵守术语表及安全显示接口；未知目标不能为了好看显示内部 ID 或真名。

## 6. 新框架下的实现方式

复用并收敛现有 `LayoutTokens`、`PanelPainter`、`TextMetrics` 与只读视图适配层。将字体、间距、状态色、选中态、表格密度和动作区域做成一致的组件规则。先核对实际使用的色板：当前自绘路径从 `pal.gd` 取 V1 色，而 `ui_tokens.json` 另含不同 palette；避免调整了配置却没影响实际界面。

战术图与特殊仪表可继续自绘；列表、输入、焦点和弹层可按现有框架使用合适控件。保持一套状态与输入分发，不为复刻早期外观重新接回旧 `state.gd` 或建立第二份战斗数据。使用旧截图作风格参考，不整体移植旧 HUD 的硬编码坐标和仿真逻辑。

呈现链路原则：业务状态/事件 → 已授权的只读视图 → 玩家文案与格式 → 布局控件；玩家动作 → 既有命令接口 → 真实结果反馈。文案层不修改业务状态。原始 reason code 与诊断日志保留，正常模式通过集中映射转成可理解文本；未知错误保留追踪入口，不伪造原因。

UI 文案逐步使用稳定键与参数模板；显示名沿用已有安全解析。禁止在代码里散落多份同义文案，也不要为了先清几句文字做全项目文本系统大重构。第一张实现卡只整理有限页面并建立可继续扩展的映射方式。

## 8. 验收标准

- 1920×1080、1600×900及约定 UI 缩放下，主要状态与动作可读，无文本遮挡/误裁切，鼠标命中区与视觉位置一致。
- 正常、未选中、长舰名、无数据、过期情报、等待授权、失联、命令失败、密集目标及多条告警均有样张；禁止只提交数据齐全时的漂亮主屏。
