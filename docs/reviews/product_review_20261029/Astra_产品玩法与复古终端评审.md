# APSIS：产品、玩法与复古终端评审

日期：2026-10-29（Asia/Shanghai）  
作者：Astra。用途：回答产品方向问题，并作为独立 Sol 文档对话的编辑依据。

## 1. 结论与证据边界

APSIS 有鲜明的核心：在不完整、过时而可能被欺骗的信息下，指挥有限兵力，与有自身任务和约束的友军协作。但系统复杂度目前不能证明游玩深度，界面功能齐全也不能证明已经形成统一的复古未来主义产品。

本次建议优先收敛决策体验与视觉语言，不再以新增系统数量衡量进度。现有工程契约和底层修复继续推进；文档整理、战役设计和 UI 设计并行进行，不要求先完成所有程序才能试验玩法。

取证使用本地可用的已合并树 `4e75897ed32f8245f35c5ec584f0ec912ec919c6`，通过 `git show` 读取，未把本地旧且有未提交改动的工作树当成当前 main。该树的 docs 与 game_v17/docs 下共有 297 个 Markdown 文件，包含审查记录和历史材料，不能把这个数字理解为 297 份都要重写的设计文档。

视觉检查使用历史图片：`mockups/gui-demo-01-v1.png`、`mockups/v1-hud-combat-1920.png`、`mockups/v1-hud-fleet-builder-1920.png`。它们不是本次运行截图。例如旧战斗图仍写 shadow，而受审树的战斗页已经接入真实弹道相关显示，不能用旧图片否定后续工程进展。本次未进行完整战役试玩、性能测量或玩家测试；下文时长和指标均为试验目标，不是留存预测。

产品范围继续采用 56 R2：剧情线外的一场完整联合战役、自由组舰、独立 AI 友军协同、明确军事目标。持续战争地图、经济造船、多人和跨战役持久化不加入首版。本报告不修改 PureWriter 原稿，也不重新定义世界观正典。

## 2. 三项应退回修订的具体设计

以下来自 `game_v17/docs/contracts/jc_sector_01_proposal.md`，该文档明确是待核对提案，不是已批准规则，更不是已完成玩法。关联 B03P 卡也明确产品尚未批准。

### 2.1 预算没有造成选择

提案第 41–64 行：预算 100、容量 3，舰池单价最高 20。即使三艘都选最贵的，也只有 60 点。因此预算约束永远不会生效；容量仍有限制作用，但点数 UI 暂时只增加阅读负担。

**修订方向：**用实际传感、火力、续航、通信能力和任务需求检验组合。预算和容量分别承担什么取舍必须写清。可以降低预算或重做价值标定，也可以暂时去掉无效点数约束；不能仅为让条形图变满而随意定价。先比较两套策略确实不同、都可完成任务的组合，验证后再锁参数。

### 2.2 友军阵容不足以呈现预期联合战斗

提案第 69–76 行：友军只有无武装侦察/中继单位。情报与通信支援有玩法价值，也尊重了当前目录武装事实；但若整场如此，用户希望的“与其他舰队协同作战”容易缩成“本方打仗、友军提供服务”。

**修订方向：**提出一个具有有限战斗能力、独立任务、资源约束和接受/拒绝条件的友军编组方案，尽量复用现有舰型和计划中的 B2 能力。要让请求友军牵制一侧、集中火力、掩护脱离等至少一种行动真实改变战局。不得给现有无武装舰暗加武器，也不顺势扩成无限舰数或多个大型 AI 系统。阵容、舰数、依赖与代价作为设计提案列出。

### 2.3 世界结果不能靠参与度改名

提案第 118–145 行建议：全部目标由友军自主完成时，判为 stalemate，以防玩家不操作也胜利。关联 B03P 卡已要求把这类轨迹标成反事实防御测试，因为当前无武装友军并不能实际做到。

**设计意见：不采用这种胜负口径。**如果世界中的军事目标确实全部达成，战区结果就应该如实记录；玩家贡献不足可写入指挥评价和战报，不能把已经完成的目标说成僵局。防止挂机通关应通过任务分工、敌方压力和玩家独有职责设计，随后用不操作对照测试来验证。不得用结算规则掩盖关卡没有需要玩家解决的问题。

这也修正了我此前“避免友军包办首胜”要求容易产生的歧义：它是关卡和协同设计目标，不是歪曲真实战果的许可。

## 3. 可玩性：需要成立的三种取舍

| 玩家决策 | 两种合理选择 | 必须真实存在的代价与反馈 |
|---|---|---|
| 是否主动探测 | 暴露自己换取较好定位；保持静默并请求其他方向观测 | 对方反应、定位质量与数据年龄发生可解释变化，不能永远主动探测更好 |
| 何时投入火力与机动余量 | 尽早打击抢窗口；保留弹药/Δv 等待更可信情报或友军就位 | 命中机会、拦截压力、后续撤离能力随选择改变 |
| 如何分配联合任务 | 自己承担突破；请求友军牵制并保护关键支援链路 | 友军有真实约束和反馈，不能总是无条件接受，也不能毫无理由随机拒绝 |

判断深度的标准是：相同界面里，局势变化后玩家会合理地改变选择。若每次都是同一套组舰、同一套授权点击、同一套开机发射顺序，系统再多也只是熟练执行流程。

主要风险包括：

- **首次新鲜感之后只剩等待。**真实轨道、通信延迟必须配合可预测窗口、可控时间倍率和必要的事件降速；玩家需要有计划可调整。不要靠不断弹警报填满时间。
- **操作量冒充决策量。**重复确认、切全屏页、逐舰做相同操作不是指挥深度。保留真实权限与命令阶段，减少不改变选择的重复劳动。
- **不确定性变成不可解释。**“为什么打偏、为什么友军没来、为什么信息旧了”必须可以从玩家已知信息和事后报告理解，不能只给失败码或全知答案。
- **自由组合名义存在，实质被固定最优解取代。**如果某支援能力永远必带，或某舰在所有维度占优，必须重新讨论任务、成本或角色定位。

### 3.1 首场战役节奏试验

先做一场约 30–45 分钟实际游玩时间的目标切片，作为设计试验；它不等于提案的 3600 模拟秒，也不是对玩家兴趣持续时间的承诺。

| 参考时间 | 玩家心智与关键选择 | 验证重点 |
|---|---|---|
| 0–5 分钟 | 明白军事目标、选择编制与主攻思路 | 不先要求读长篇百科；能解释为何选这些舰 |
| 5–12 分钟 | 首次接触，决定用暴露还是等待换情报 | 出现第一项有代价的选择和可理解反馈 |
| 12–22 分钟 | 自己与友军分工，承诺一次进攻/牵制窗口 | 协同改变空间关系或时间条件，不能只是加成按钮 |
| 22–35 分钟 | 原计划受到一次可解释的敌方反应或资源压力 | 可以修正计划；不是强制脚本惩罚或机械加波次 |
| 35–45 分钟 | 选择继续达成目标、止损或撤离，阅读战报 | 能说明自己怎样影响结果，并想到下一次不同做法 |

这些是体验节奏的参考区间，不显示成“Phase 1/2/3”，不强制所有玩家在同一时刻经历同一事件；按局势和玩家行为推进。

### 3.2 如何证伪“很好玩”

首轮找 3–5 位目标玩家做观察测试，只作定性诊断，不据此声称统计留存。记录首次独立决策时间、无事可做的等待、重复切页/点击、失败归因与第二局选择。

- 简报后能复述本场目标和一个行动风险；约前 5 分钟能独立作出一次有代价的选择。
- 两种编制均可完成任务，且实际打法与资源压力不同。
- 与“玩家不操作”“不请求友军”对照比较，确认玩家行动与协同确实改变结果。
- 连续约 60–90 秒没有新信息、计划调整或有意等待理由时，记录为节奏审查点；不是要求每分钟强塞事件。
- 战败者能指出关键决定及其后果；愿意再试者能提出不同方案，而不只是期待运气变好。

先争取一次完整且愿意重玩的战役，再讨论数小时乃至更长寿命。时长来自可重组的问题、不同敌方反应与可比较策略，不来自文档厚度或更多舰名。

## 4. 复古未来主义：当前距离与明确方向

早期 gui-demo 的轨道弧、大小读数、局部仪表和主次关系，比后续部分全屏表格式页更接近目标。它的微小文字和偏暗信息不应照搬。当前新框架能承载目标，但需要产品层面的重新组织。

| 层面 | 已有基础 | 仍需完成 |
|---|---|---|
| 图形语言 | 深色底、磷光绿、轨道几何、线框、共同绘制组件 | 主次字号、符号规范、功能区比例，以及持续一致的设备身份 |
| 操作体验 | 对象列表、详情、命令与状态视图 | 战术操作期间保留态势上下文，减少通用全屏表单与来回切换 |
| 屏幕质感 | 旧路径已有轻微 CRT 效果 | 接入实际入口、选择适合的显示技术、按层分配效果、验证缩放与阅读 |
| 动态与声音 | 可复用已有音频和界面基础 | 回执、状态跃迁、刷新与提示音共同表达真实事件，而非装饰性随机闪烁 |
| 文案 | 60/61 已有规范、术语及候选台账 | 接入状态映射、削减工程说明、真实运行中复核无数据/过期/失败等边界 |

**关键代码证据：**`game_v17/shaders/crt.gdshader` 已有扫描线、颗粒、暗角、轻微色散、反光和闪烁；受审树中它由 `scripts/main.gd:123` 创建使用。正式 orbital_sim 剖面进入 `v1_hud.tscn`，其场景及 `scripts/ui/v1_hud.gd` 初始化未接入该材质。这个 shader 也没有时序余辉或亮部扩散的独立实现；扫描频率写死按 1080 高度计算。由此只能说旧效果可作起点，不能宣称当前正式 HUD 已有完整屏幕拟真。

### 4.1 从《异形：夺命舰》借鉴什么

影片屏幕设计负责人 Jason Forrest Hogg 的[项目说明](https://forresthogg.com/projects/alien-romulus-gfx)把殖民地终端定义为朴素的企业办公工具，并根据旧运输船和较新空间站区分屏幕与字体；特定警报的模拟失真还经过硬件视频合成器处理。这里可借鉴的是设备用途、年代和内容之间的一致性，而非照抄影片版式或把所有画面一律染绿。

APSIS 推荐采用“在役轨道舰队的工业战术工作站”作为主 HUD 身份：固定功能区、明确模式、成组硬键、必要的制式编号、矢量态势和少量大读数。中文使用可读正文字体，数字/单位使用稳定等宽或表格数字；不把每个标签都中英重复，也不把中文硬压进微型像素字体。

### 4.2 图形、材质、行为分开设计

1. **先完成无特效版。**关掉一切屏幕效果，仍能在 1920×1080、1600×900 与约定 UI 缩放下读懂任务、对象、风险和动作。延续 60 的主文字 14–16px、次要 12–14px 首轮建议，实际以字体测量和阅读为准。
2. **主屏保留态势。**战斗中把所选目标、传感、火控或协同细节放在稳定侧区/可展开区域；编制、数据库和战报可用专用整页，不能要求所有任务都挤在同一小栏，也不让每次发命令都遮住整个战场。
3. **材质按显示类型分配。**主战术矢量显示可有克制的亮部扩散和短余辉；光学视频可使用独立噪声与信号衰减；终端正文优先清晰。单色显示的核心不应是 RGB 彩边。不要同时叠满桶形失真、模糊、颗粒、色散、扫描线和闪烁。
4. **区分数据旧与屏幕旧。**战术轨迹的数据年龄、旧报告、失联由真实状态表达；残影只是显示外观，不新增可点击目标或过期真值，不用随机故障假扮信息战。关键数据更新不为仿旧而额外拖延。
5. **事件驱动动效。**模式切换、命令送达、拒绝、执行完成有不同且克制的反馈；日常更新保持安静。强失真只限短暂、可解释的场景，并提供减弱/关闭选项；不能遮蔽必须立即阅读的警报或命中区。

以一个同数据、同布局的“清晰版/屏幕效果版”战术样页先比较。清晰版不成立就先改图形层级；效果版损害识别速度就回调。不要直接给所有覆盖页上滤镜后宣布美术完成。长期看电影画面几秒和操作战术界面几十分钟是不同的阅读任务。

## 5. 文档应怎样重构

我此前 56 需求偏重系统接通和验证，60 偏重可读性与文案清理；它们仍有价值，但未充分定义决策密度、设备身份与显示效果。此次补充这些设计职责，不要求 Sol 或 DeepSeek 自行猜测。

不是先改所有措辞，而是建立清楚的适用范围和权威关系：产品范围、世界观/叙事、玩法规则、UI/玩家文案、工程契约、执行/验收、历史档案。每个主题只有一个当前入口，相关历史通过链接查阅。

需优先处理的例子：

- 18 的“默认不交火、开火是灾难”属于旧剧情场景，不能全局套到联合战役；保留其剧情语义，标明适用模式。
- 35 要求沿用旧字号/密度，与 60 的可读性要求需要明确优先关系；继承视觉语言，不永久冻结旧像素尺寸。
- 09 与 ui_v1 把多轮交付记录附在设计规范中，容易混淆当前行为与某一轮临时边界。
- 59 是持续追加的执行历史；读者需要一个当前状态摘要，具体轮次证据保留在审查档案中。
- B03P 的预算、友军与结算提案需要先修订设计，而非只润色为更顺口的玩家文案。

每份当前文档至少注明：适用产品/模式、状态（已确认/提案/实现说明/历史）、负责人、来源与取证提交、取代或被取代的文档。对工程实现状态保留证据日期，不因文档编号大就自动成为更高权威。

每项玩法写清：玩家面临的问题、可选行动、信息来源、代价、延迟与结果、UI 反馈、失败后的解释。每项玩家文案写清：触发状态、显示位置、语义、操作后果；开发边界移入诊断，但不删除“尚未收到”“过期”“拒绝”“不可用”等必要区别。

原文先保留，先交导航、冲突台账、替代稿及链接迁移计划；确认替代内容完整后再处理归档和原位置提示。此轮不执行无差别删除、不大改正典、不把工程验收记录当作可丢弃的杂文。
