# JC-A01 save/load focused review (candidate `1d1e8399da438b77b74acee40d753711c8d2a8f9`)

## Findings

1. **Legacy TrackTable data is not migrated into the player's new intel owner.** `GameSession.load_state()` restores the legacy `track_table` snapshot first ([game_session.gd:4848-4860](../../../game_v17/scripts/core/game_session.gd:4848)), but when `authority_intel` is missing, `AuthorityIntel.import_state({})` only accepts empty owner maps as legacy and returns without copying legacy tracks ([authority_intel.gd:272-276](../../../game_v17/scripts/core/authority_intel.gd:272)). Repro: create a valid session, add one TrackTable observation, save, remove only `authority_intel`, load. Load returns `ok=true`; restored `track_table.all_tracks()` contains `T0001`, while `intel_view("player_intel")` and `intel_view("ally_intel")` are both empty. This drops the old single-owner contacts from the new player-facing facade instead of migrating them to the legacy own-ship domain. The load result also exposes only sensor restore labels at [game_session.gd:5195-5198](../../../game_v17/scripts/core/game_session.gd:5195), so callers cannot distinguish authority legacy migration from a full restore.

2. **A malformed present authority section is silently accepted as a legacy save.** `load_state()` converts every non-Dictionary `authority_intel` value to `{}` ([game_session.gd:5174-5182](../../../game_v17/scripts/core/game_session.gd:5174)); `import_state()` treats an empty dictionary as a valid legacy-missing section ([authority_intel.gd:273-276](../../../game_v17/scripts/core/authority_intel.gd:273)). Repro: take a valid new save and replace its `authority_intel` value with the string `"broken"`. `load_state()` returns `ok=true` and all owner views are empty. In contrast, changing the nested segment version to `999` returns `ok=false`, `invalid_version`. This bypasses the existing damaged-new-save rejection behavior by turning malformed-present into absent.

## Focused positive evidence

A temporary headless diagnostic wrote `GameSession.save_state()` to a real file under `.test-results/sol-a01/save/authority-roundtrip.json`, closed it, read it back, then loaded a fresh session. The exact file contents matched the in-memory save; player, ally, and opfor views matched immediately and remained equal between the original and restored sessions after 10 further ticks (session time 16.0 s). This is a same-implementation comparison, so it establishes file serialization/reload preservation for the tested rows, not independent expected-value correctness.

The shipped `jc_authority_intel_probe.gd` R4 is narrower than that evidence: it compares only player intel and continues two in-memory sessions after `save_state()`/`load_state()` ([jc_authority_intel_probe.gd:210-225](../../../game_v17/tests/jc_authority_intel_probe.gd:210)). It does not itself write a file or compare ally/opfor state, and its delayed shared example is directly inserted as a received observation rather than saved while pending in transit. No conclusion about pending shared-message persistence is claimed here.
