# JC-B03P：阶段性战区行动的具体内容与目标提案

执行Issue：[JC-B03P #63](https://github.com/HATO-24/ghost-track-apsis/issues/63)。

状态：READY内容设计；先用B00草案，最终对齐K0；交付P0。公共规则见[总队列](../../59_联合战役Demo_R2_范围与下一批任务卡.md)。

## 1. 目标与已确认边界

把用户已经确认的“阶段性战区行动、自有舰队直控＋友军请求”变成可审查的具体战役方案；解除第33舰队某战区部队有组织作战能力，结算为去军事化的阶段性成果。不能再将整支第33舰队覆灭当默认首胜，也不能只写抽象“歼灭所有敌人”。

## 2. 基线与范围

调查起点C55=`30b8d33dae9787aadf89bb206757cafb2cad7bd3`；内容契约最终对齐K0精确SHA。范围为战区提案、数据/事件轨迹fixtures、简报/通信/战报文案与验收脚本；不改主线Mission/存档、不实现裁决运行层/AI、不将提案直接设为默认正典。与B00技术契约同步但不阻塞其独立设计。

## 3. 数据、读者与时间

提交scenario_id、候选战区/日期、参战舰池/点数、两套示例编制、友军/敌方/目标对象及其稳定引用。权威裁决未来可读系统状态，但玩家目标面板只读已获情报/战报，未知敌方目标不能直接暴露名称/坐标/损伤。明确truth状态、observed状态、报告时刻与未知/待确认语义；story=false也运行目标。

每条目标写：对象、军事属性、进入/完成/失败条件、证据来源、可否本场恢复、玩家可见反馈、终态及优先级。时间单位模拟秒，日期不混进模拟tick；各阶段事件有ID，重复/迟到/读档不能重复裁决。

## 4. 具体工作与提交拆分

1. 给出一套主提案及必要备选，标明建议值/依据/待用户核对项。起点可用“2个指定军事作战单位丧失本场有效射击能力＋1个明确军事指挥节点丧失行动能力”；只用已有或明确排期的能力，暂时失联/EW/停火不能当不可恢复失能。
2. 给出舰池与指挥容量/资源具体点数、两套合法且战术不同的编制、至少1支独立AI友军、最小敌方守卫/攻击/撤退规则；说明何种差异必须在后续真实运行验证。
3. 逐步写简报→组舰→部署→首次协同→交战/撤离→裁决→战报。支援目标/掩护/撤离请求各写接受、拒绝、执行中、失联/受损、结束或失败回执样例；每个阶段需要玩家做什么、友军如何实际影响局势写清楚。
4. 具体提出胜/败/主动撤离/僵局/时限与冲突优先级；等待时长只能触发规定终态，不能替代军事目标。设计玩家有效贡献及友军贡献报告，避免玩家无操作仍由AI包办首胜。不得强迫屠杀平民或破坏民用设施获胜，不偷偷加入完整登陆/投降系统。
5. 交文案/目标表，再交语义校验fixtures与用户待决定表；目标运行层留B3a，内容接入留B3b，当前不伪造可玩完成。

## 5. 正负例与兼容方案

至少提供假想事件轨迹：完整胜利、目标失能但尚未获报告、失败、主动撤离、超时/僵局、友军拒绝/失联后替代路线；临时通信中断、单次EW、重复事件不能误判去军事化；任务对象仍能战斗不能计失能。相同轨迹保存/继续与同tick顺序应有唯一预期终态，不重复结算。

轨迹只校验内容逻辑，不是实际AI/战斗/读档通过证据。旧主线、旧seed/存档保持原行为，未来模拟器独立入口/schema迁移列清；若某终态依赖未实现机制，必须标依赖与替代提案。
