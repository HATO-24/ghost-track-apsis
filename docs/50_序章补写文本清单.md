## 0　使用规则

1. 本清单只列 **key / 用途 / 来源行 / 依赖 / 状态**；不写对白、不写旁白、不写最终标题。
2. 提案 key 使用 `TXT-0601`–`TXT-0648` 段（现有 `docs/23` 到 `TXT-0507`；本段为**待并入**的提案号，最终编号由 Lead/23 统一）。
3. 所有文本进入游戏前必须走 17 的文本审批；先由用户润色，再写入 `data/`/`HUD`/`story`。
4. 未定人名/地名用占位：`{副官名}`、`{前任名}`、`{玩家名}`、`{登记号}`；不得在代码里硬编码。
5. 复用 15/23 已有文本的条目，在 §2 末尾单列，不重复写新文案。
6. **不写最终文案**：本清单的“用途”只说明该 key 要解决什么文本需求。

## 4　写作约束（给最终写作者）

1. **文风**：说明性、事实优先；军队通话用完整句、程序词、单位/批号；敌对方礼貌、程序化。
2. **不抒情**：不写“最残忍的地方”式句子；不写“天选者/救世主”式自我评价；不写旁白解释设定。
3. **通信格式**：`[发信者至收信者]-[LD/LR/RDO/IR/VIS]-[内容]`；教学/副官建议不进通信流（19 §7）。
4. **职责边界**：46 管编制、47 管人物、48 管事故、49 管编号；50 只列 key，不替 46–49 写设定。
5. **不覆盖 legacy**：复用 15/23 时保持原文，除用户批准的 D2 换词。
6. **不编造**：44 未给的姓名/日期/结局细节用 TBD 或占位；不写官方未确认的“真相”。
7. **审批**：先由用户二次核对 47/49 的人名/编号，再按 17 的流程把文本写入 23/数据。
